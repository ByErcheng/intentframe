# 外部 AI 使用说明

本页供通过 MCP 使用 intentframe 的外部 AI 在工作前阅读。用户说明要做什么视频、用途、反馈和确认；外部 AI 应能依据本页和当前连接公开的工具定义，确定调用顺序、准备正确参数、识别结果并处理错误，完成交接、查询、审查和交付。业务规则分别以[制作流程](../docs/workflow.md)和[数据约定](../docs/data.md)为准；[MCP 工具入口](../src/mcp/server.ts)是系统维护时的实现依据，正常使用无需先阅读源码。

MCP 连接时提供阅读指引；调用 `read_usage_guide` 即可取得本页原文、版本摘要和章节清单，无需直接读取系统仓库。详细制作或数据规则可指定 `document:"workflow"` 或 `document:"data"`，再用返回的章节名称指定 `section` 按需展开。当前支持范围与证据边界见[说明交接与后台执行](../docs/architecture.md#外部-ai-说明交接与后台执行)。

升级后须重启 MCP 连接并重新读取工具定义，避免使用旧参数。能力状态统一见[当前实现与下一步](../docs/architecture.md#当前实现与下一步)。

## 外部 AI 的工作约定

- 开始任务前读取本页，调用 `get_runtime_info` 了解已配置的资产总目录和制作区域。路径以服务返回值为准，用户无需在每次需求中填写或核对固定路径。缺少访问权限或服务目标与已知配置不一致时说明具体问题，不能自动换目录继续。
- 根据用户的自然语言确定目标和测试或正式用途，再准备工具参数；只有影响执行的关键信息无法判断时才询问。操作编号、分页、任务定位和运行状态查询由外部 AI 处理，用户不必提供技术调用步骤。
- 常用制作交接按本页[固定请求模板](#固定请求模板)填写，使用当前工具支持的字段；将用户原话与执行解释区分，不凭自由文本另造请求格式。工具定义或模板与实际能力不一致时先核对，不能猜测字段继续发送。
- 首次提交本轮需求或反馈前，使用下方[发送前任务展示模板](#发送前任务展示模板)向用户展示实际任务。展示与自动发送的边界按[请求准备与内容确认](../docs/workflow.md#请求准备与内容确认)执行；实质改参时更新说明，取得回执后及时告知保存或受理结果。参数返回给 AI 不等于已向用户展示。
- 使用项目工具交接制作要求，由项目主 AI 制作与修改。先查已有任务和反馈，再决定新建还是接续；以原始需求、仍有效的反馈及已保存状态为依据，不能只靠当前聊天记忆。
- 新任务先保存外部准备的 Markdown 草稿，用户明确交接后设计，外部 AI 实际读取稿件及附件后记录采用，再制作代码。AI 采用设计不表示用户认可成片；旧任务保留原样例确认规则。
- 稿件生成、素材导入/生成、制作、材料准备、渲染、经验整理和恢复工具受理后返回执行编号，由本机工作进程继续处理；随后按编号查询。已受理不等于已经完成；断线或超时后沿原编号核对，结果未知时保留保护。
- 交付时返回真实文件入口、任务与版本、完成范围和未解决事项。面向用户解释创作结果与需要决定的问题；技术细节仅在排查或影响决定时展开。不能实际观看视频时，明确审查范围。

以下各节供准备参数和处理对应情况时查阅。MCP 已连接时直接使用其工具；需要命令行调用时，先完成[本机配置](../config/README.md)，并在仓库根目录执行。示例中的 JSON 文件位置须替换为任务实际路径，真实需求与请求保存在本机数据目录。CLI 与 MCP 共用业务实现。

## 发送前任务展示模板

这是面向用户的固定展示格式，与发给工具的 JSON 参数模板用途不同。每次保留以下字段和顺序，替换尖括号内的说明，不把占位文字原样发送。不适用的项目明确写“无”并在必要时说明，不省略字段；内容较多时可以在对应字段下展开。

```text
本轮任务：<作品名称与本轮目标>
用途：<测试 / 正式，必须明确填写其中一个>
本轮阶段：<草稿保存或修订 / 设计 / 素材准备 / 样例或完整制作 / 材料准备 / 反馈，按实际操作填写>
修改基线：<版本与方向；首次制作写“首次制作，无基线”>
你的要求：<准确保留用户本轮要求，不混入 AI 自行决定的内容>
我的执行解释：<具体做法及由 AI 自行作出的选择；无额外解释则写“无”>
保留要求：<继续有效且本轮不能改变的内容>
本轮交付：<将生成或保存什么，以及本轮不包含的必要范围说明>
未定事项：<尚未确定的事项及本轮如何处理；没有则写“无”>
```

“用途”对应测试或正式的数据归属，不能用“样例”代替；正式任务也可以先制作样例，测试任务也可以测试完整制作流程。新作品按用户要求确定用途，已有作品沿当前任务记录填写，与实际请求及目标作品一致；无法确定或与用户要求冲突时先澄清，不能默认填“正式”或擅自切换保存区域。

已有授权且没有阻塞执行的缺口时，展示后自动提交，无需用户再次批准；有关键缺口时，明确说明暂不提交并提出具体问题。不要把模板展示记作用户方向确认或成片认可。模板正文仅在本节维护。

## 一次制作的调用顺序

外部 AI 负责沟通、调用与审查，项目负责设计、制作、文件落盘及检查材料准备。用户可在任何客户端整理草稿；发送给项目的内容必须保存。写操作均先准备稳定 operationId，耗时操作受理后用 get_execution 查询。

| 阶段 | 调用 | 继续条件 |
| --- | --- | --- |
| 查入口与任务 | read_usage_guide、get_runtime_info、list_works/get_work | 核准用途与已有任务；不得猜路径 |
| 保存草稿 | create_work 的 brief 保存为首版原文和 d001；后续 submit_draft 提交完整 Markdown | 只保存，不自动开始设计 |
| 按意见改稿 | revise_draft 交给项目 AI，或 submit_draft 保存外部改好的正文；都指定基线 | 返回新稿供用户与外部 AI 讨论，旧稿保留 |
| 用户交接 | handoff_draft，填写用户明确开始设计的原话与草稿引用 | 草稿的默认保存或一般好评不代替交接 |
| 项目设计 | design_video，基线为已交接草稿或其设计稿 | 只形成脚本，不生成视频源码 |
| 外部审查设计 | read_document 读正文与附件，review_design 记录 adopted 或 needs_changes | 范围内 AI 可采用；关键用户意图缺口才回问 |
| 准备素材 | import_asset、generate_image、read_speech_text/synthesize_speech | 保存真实文件与来源；未配置服务不假装生成成功 |
| 代码制作 | produce_version，明确 designRef、assetIds、基线与反馈 | 样例/完整制作都按本轮采用脚本；主 AI 可在已定范围内自主实现 |
| 项目准备材料 | 新流程制作后自动抽帧与覆盖核对；必要时 prepare_review_materials | 项目保存帧图、拼图、时间索引、混音及补帧批次 |
| 外部审查 | get_review_materials，实际读取后 record_review | 关联实际用到的 materialIndexes，不能用材料可用代替审查通过 |
| 修改与交付 | 按原任务提交反馈、更新必要设计并制作新版本；返回实际文件 | 用户对完整成片明确认可后才记录 acceptance；发布授权另行处理 |

有 authoring 的任务使用新流程。没有 authoring 的历史任务沿原样例与确认规则接续，不批量补造稿件；提交草稿可显式启用新流程。现有比较入口保留旧的一次首稿比较方式；测试新交接流程请创建独立 test 任务，不把旧比较入口当作已验证的新流程效果比较。

## 交接内容与进度说明

向用户说明本轮实际交接的目标、用途、制作范围、保留项、修改项和未定事项，区分用户原话与 AI 整理要求。准备完请求不等于已经发送，调用返回前不能声称项目已经收到；以实际保存内容及回执为依据，必要时附可查阅入口，不要求用户逐项批准正常技术参数。

取得回执后区分需求已保存、制作已受理、正在执行、等待补充、明确失败、结果未知和完成，并说明最后一次实际核对时间。制作受理回执及执行查询的 `selection` 显示实际采用的基线、反馈编号和方向选择。最终查询的 `timing` 记录项目接收至首次最终返回的[总耗时](../docs/workflow.md#时间与耗时)；当前作品查询按操作编号返回 `executionTimings`。不要求外部 AI 提供发送时间，旧请求缺值不能估算补写。恢复后原计时保留 `firstReturnedStatus`，不能将原失败回复的时长改称恢复成功耗时。

原操作回执与执行结果中的作品摘要是历史快照。交付前通过 `get_work` 核对当前版本和文件可用性，不把旧快照的占用或可用性称为现在的状态。查询显示终态也须核对实际版本，不能仅凭文案认定作品通过审查。

当前作品查询的 `availability` 表示工程与视频是否可核对，`previewAvailability` 另行报告预览状态、可用路径与缺口。返回的 `technicalCheck.previews` 仅保留本次可交付路径，原任务文件中的历史检查记录不因查询被改写。视频可用而预览缺失时仍可交付视频，随后用 `render_version` 从原视频补图；这不重新调用模型、渲染或替换视频，也不改变认可。

文件在本机可用时，直接返回绝对路径、作品与版本、本轮完成范围、实际检查范围及待用户判断事项。压缩或复制不是固定交付前提，不能因准备附件而不提供已可查看的本机结果；未实际播放过的内容如实说明。

## 用途与查阅

一个 MCP 连接处理两种用途。用户说“做测试”时，外部 AI 在 `create_work` 中传 `purpose:"test"`；用户要求正式制作时传 `purpose:"production"`。新任务必须明确用途，无法从需求和上下文判断时才询问，不猜测默认值。后续工具只传原 `workId`，程序按记录定位；制作、反馈、渲染和恢复均不能通过额外用途参数改写原任务。

`get_runtime_info` 不写文件，返回 `assetRoot`、`workRoots`、`knowledgeRoot`、`scopeIds`、执行方式与说明入口；尚未首次写入的区域没有区域标识。启动配置只确定整体存储位置，不承载本轮任务用途。升级方式见[正式与测试入口](../config/README.md#正式与测试入口)。

`list_works` 默认列正式区域，显式传 `purpose:"test"` 或 `purpose:"all"` 可查测试或两类任务；列表筛选不影响后续操作。`get_work` 按编号自动查回任务。返回的 `purpose` 是原记录用途，`storagePurpose` 是查找到的区域，历史用途未知时不能把两者混同。两类查询支持 `offset` 和 `limit`，默认每页 20 条，最多 50 条；`nextOffset` 不为空表示仍有内容。任务详情中各类列表使用同一偏移量，并报告总量；完整事实从返回的任务文件与原始需求路径读取。

新反馈原文以独立追加文件保存，`get_work` 已合并任务快照与反馈记录，并返回 `feedbackDirectory`。手动读取文件时也须核对该目录，单独读取 `task.json` 可能遗漏制作期间追加的意见。`appliedInVersionIds` 表示实际在哪些版本处理过，`supersededByFeedbackIds` 表示被哪些后续意见替代；收到、应用和替代是不同事实。

## 请求准备与重试

所有写工具都要求 `operationId`。先准备并保存请求，再执行；同一次操作原样重试使用原 JSON，不再次准备。新业务操作使用新编号；错误请求需要改参时，先按[请求错误与纠正](#请求错误与纠正)核实原操作的影响，再准备更正请求。编号区分操作，不是用户身份。

通过 MCP 时，按下方[固定请求模板](#固定请求模板)调用 `prepare_operation`；将返回的 `arguments` 完整保存，再把这个对象作为对应目标工具的参数发送。目标工具不接收外层的 `name` 和 `arguments` 包装。准备不会创建作品或开始制作。

准备成功说明请求格式通过了检查，并回显技术默认值；它不查询作品、版本或方向确认。目标工具在受理前检查可确定的业务条件，执行时再次核对可能变化的状态。发送前仍按本页选择实际范围，不能把准备回执称为制作受理。

通过 CLI 时，原始参数文件只保存对应模板的 `arguments` 对象，不包含外层包装或新操作编号。例如创建任务：

```sh
# 只生成请求，不执行制作；输出文件必须尚不存在。
./scripts/intentframe prepare create_work /绝对路径/原始参数.json /绝对路径/创建请求.json

# 创建记录，返回作品编号与任务文件位置。
./scripts/intentframe call create_work /绝对路径/创建请求.json
```

CLI 的 `prepare` 生成操作编号并将完整调用参数保存到指定文件，再用 `call` 发送该文件。已有调用方也可以自行生成稳定编号，但必须在首次发送前持久保留。

同编号同内容的成功请求返回原回执，同编号不同内容被拒绝。后台请求的原回执记录“已受理”，执行结果另行查询；重复提交仍返回相同受理编号。超时后先调用 `get_operation`（参数为原 `operationId`），再按回执中的执行或作品编号查进度。原操作尚无确定回执时，不能换编号重做；也可从 `get_work` 返回的 `activeExecutionId` 找到待核对的后台执行。

新操作编号在整个资产目录内唯一；改变用途也不能重复使用。旧测试区域中的回执仍可原位查询、补存和重试。旧创建请求原本不带用途字段，重试时须补齐原用途，其余内容保持一致；系统核对后返回原回执。若历史两区域恰好有相同操作编号，`get_operation` 可附 `purpose` 明确查询对象，写操作仍阻止猜选。记录损坏、缺失或任务编号重复时明确失败，不改号或改区域重做。

## 请求错误与纠正

请求格式或数据不符合要求时，项目返回纠正提示。准备与业务前置校验的提示包括 `tool`、`issues`（字段或对象及原因）、`effect` 和 `nextStep`；MCP SDK 的结构校验也可能直接返回协议错误文字。已提前检查基线、反馈引用、方向确认等可确定条件；受理后仍可能因环境变化或真实执行失败而结束，必须查询实际结果。规则见[请求校验与纠正反馈](../docs/workflow.md#请求校验与纠正反馈)。

### 怎样识别和处理错误

1. 读取工具实际返回的错误内容。MCP 调用可能直接报参数错误，也可能返回 `isError:true`；CLI 失败时查看错误输出与非零退出状态。后台工具已经返回受理编号时，继续用 `get_execution` 查看对应执行的 `status`、`error` 和结果，不能只检查最初的受理回执。
2. 核对出错字段或对象，并查当前工具定义、原请求和必要的任务记录。可以确定的格式、类型、编号引用错误由外部 AI 自行纠正；用户意图、作品目标或确认范围不明确时才询问用户。不能为了通过校验而编造编号、确认原话、位置或截断必要需求。
3. 按下表决定是准备更正请求，还是继续核对原操作。错误信息不足以判断是否已经产生影响时，保留原编号与错误依据，报告待核对项，不盲目尝试新编号。
4. 更正请求通过准备后保存完整参数并调用目标工具；取得成功回执后才说明已保存或已受理。仍然失败时根据新增错误继续核对，不能原样重复发送同一错误内容。

| 已取得的事实 | 外部 AI 的下一步 | 编号处理 |
| --- | --- | --- |
| `prepare_operation` 明确校验失败，目标写工具尚未调用 | 按提示修正原始参数，再准备请求 | 尚未执行业务，不使用虚构的准备结果 |
| 目标工具明确因参数或前置条件拒绝，且已核实未产生业务影响、没有未知执行 | 修正错误，或先补齐缺失条件，再准备更正请求 | 更正请求使用新操作编号；已登记的旧编号不能换内容 |
| 同编号内容冲突 | 找回该编号最初保存的请求，查询其回执，确认是误改原请求还是确有新操作 | 原样重试恢复原内容；只有新操作已明确且原执行已核清时才用新编号 |
| 已受理、执行失败、原回执未定、超时或回复丢失 | 查询 `get_operation`、`get_execution` 和必要的 `get_work`，按实际结果继续或恢复 | 保留原编号；单独看到 `failed` 或“未找到回执”不能证明没有产生影响 |
| 数据损坏、占用归属不明或当前接口无法表达所需范围 | 说明阻塞原因与需要核对的对象，保留已有记录 | 不改号绕过、不删除记录或占用 |

### 常见问题与修改方向

| 问题 | 应怎样纠正 |
| --- | --- |
| 缺少 `purpose`、枚举值拼错、字段类型不符、额外添加未支持字段 | 按工具定义补齐或修正；用途来自用户要求，不能为了通过而随便选值 |
| 把模板的 `name`、`arguments` 外层包装发给目标写工具 | 包装只发给 `prepare_operation`；目标工具接收准备返回的完整 `arguments` |
| 作品、版本或反馈编号不存在，或不属于本次作品 | 用查询取得真实编号，核对目标与原话；不能通过改成“最新版本”猜测用户所指对象 |
| 历史基线缺少选择理由，或 `resume` 的基线没有原生线程 | 核对工程后补充真实理由；只有确实可以新会话接续时才选择 `fresh` |
| 缺少适用方向确认，或基线没有延续已确认样例 | 先查已有确认及其范围，缺少时返回样例取得用户确认；`baseReason` 不能代替确认 |
| 反馈定位超过已核实时长，或把未核对的位置标为精确 | 回看目标版本核对位置，按实际证据修正；不能仅修改标记来掩盖错误位置 |
| 不需要再处理反馈，或只需要部分意见 | 明确使用 `feedbackIds:[]` 或所需编号数组，不通过省略来表示空集合 |

例如准备创建请求时漏填 `purpose`，`issues` 会指出该字段及允许的 `production`、`test` 值，要求核对后纠正。前置校验所说“本次请求尚未进入业务执行”只针对当前请求，不表示原操作没有产生效果。运行错误、未知状态及残留占用仍须按原编号核对。程序能检查格式、存在性、归属和已保存的前置条件，不能保证 AI 正确理解用户意思。

## 制作前核对基线与反馈

新流程另须先读取并核对 designRef 对应的采用脚本。设计与工程基线是不同引用，素材来自稿件附件和本次显式选择；用户重新交接草稿或新增方向变更意见后须重新核对设计采用。

本节适用于 `produce_version` 的样例、修改和完整制作。**反馈指向哪个版本、从哪个工程继续、这轮处理哪些反馈，是三个不同选择。**

| 请求内容 | 当前实际行为 |
| --- | --- |
| `baseVersionId` | 指定本次复制并继续编辑的工程。省略时优先延续已确认方向内最新可核对工程；无确认且有多个已记录方向，或后续旧版本方向不明时要求明确选择。已有版本仍建议显式填写 |
| `baseReason` | 解释基线选择及后续修改如何保留。选择非最新工程时必填；理由不会改变程序选入的反馈，也不会替代方向确认 |
| 明确填写 `feedbackId` | 只把这一个反馈编号列为本轮处理目标；仍须核对它适用于所选基线。反馈目标版本不会自动成为制作基线 |
| 明确填写 `feedbackIds` | 以数组列出本轮实际处理编号，`[]` 表示不处理反馈，可选择一条或多条；与 `feedbackId` 不能同时提供 |
| 同时省略两个反馈参数 | 选择当前基线方向内尚未继承的有效反馈，排除明确被替代的意见及已完成的备选创建要求；历史范围无法核对时返回提示，不等于选择空集合 |
| `newDirection` | `true` 表示从所选工程创建新的备选方向，只允许样例；省略或 `false` 表示沿用基线方向。新增备选不自动撤销原方向确认 |

推荐使用明确的 `feedbackIds`，并说明哪些事项留待后续。空字符串、`null`、重复编号及已被替代的编号会被拒绝；不能编造反馈来模拟空集合。创建备选时，原方向继续有效的反馈使用 `changesDirection:false`，制作请求使用 `newDirection:true`；确实改变或撤销已确认方向时才按原话设置 `changesDirection:true`。

### 核对本轮实际选择

1. 用 `get_work` 取得当前作品，沿 `nextOffset` 查全所需版本和全部反馈；不能把第一页的空列表当作没有其他反馈。确认原执行已经核清，再选定本次工程及适用方向确认。
2. 核对基线的 `directionId`、来源关系与已处理反馈。旧数据没有方向信息时不补造；按提示选择有依据的基线，历史基线说明后续修改如何处理。
3. 根据本轮需求明确选择反馈编号，核对其原文、目标和 `supersededByFeedbackIds`。要替代或取消旧要求，先用新反馈的 `supersedes` 引用旧编号，保留原文与变更依据；不能删除旧反馈。
4. 保存并发送准备好的请求，核对受理回执的 `selection` 是否与实际选择一致；向用户说明范围和保留事项。若选择默认范围，更须核对实际选入的编号，而不是仅凭“最新版本”或“已经处理过”的印象。

| 本轮真实要求 | 正确调用方式 |
| --- | --- |
| 不处理反馈 | 使用 `feedbackIds:[]`，明确填写已核对的基线 |
| 处理一条或多条明确意见 | 在 `feedbackIds` 中列出实际编号，其他意见保留且不宣称本轮已处理 |
| 按该方向全部有效的待处理意见继续 | 可以省略两个反馈参数，核对受理结果中的实际选择；希望完全控制范围时仍应显式列出 |
| 无法可靠确定基线、继承关系或适用范围 | 继续查询或澄清关键选择，不能把不确定当作空集合 |

**旧任务两种方向的例子**：`v001` 是已确认的 A，以它为基线用 `newDirection:true` 制作 `v002` 作为 B，保留 A 的确认。用户选回 A 且不需处理新反馈时，完整制作明确传 `baseVersionId:"v001"`、真实 `baseReason` 和 `feedbackIds:[]`。已记录的新方向不会改变 A 的默认选择，已完成的 B 创建要求也不会自动再执行。旧数据缺少方向标记时同样可以显式选择有依据的 A 与空集合，不批量猜测历史方向。设计依据见[方向与反馈的适用范围](../docs/data.md#方向与反馈的适用范围)。

## 草稿与设计调用

create_work 只接收正文，不要求用户先在本机建立文件。read_document 参数为 workId 和 ref（id、sha256），返回正文、本机位置、附件与来源。sha256 来自工具回执，覆盖正文和实际附件，不自行计算或从文件名猜测。

| 工具 | 关键参数与含义 |
| --- | --- |
| submit_draft | workId、markdown、instruction；已有草稿必须 basedOn 最新引用。assetIds 省略继承基线附件，[] 明确不采用附件 |
| revise_draft | workId、base、instruction，可选 assetIds；项目模型只改稿，结束后返回新正文 |
| handoff_draft | workId、draft、userInstruction；仅转录用户明确交接原话 |
| design_video | workId、base、instruction，可选 assetIds；base 可为交接草稿或该草稿的设计版本 |
| review_design | workId、design、status（adopted/needs_changes）、source（external_ai/user）、notes；须先实际读过内容 |

三个稿件工具的 assetIds 都表示本轮完整附件选择，省略继承，空数组清空；最多 20 个。附图来源与用途由素材的 description 和 origin 表达。项目只把图像附件送入模型视觉输入，音轨仍通过原文件与元数据说明，不虚构听音结果。

例如，以下对象交给 prepare_operation，编号与摘要替换为真实回执值：

```json
{
  "name": "design_video",
  "arguments": {
    "workId": "work-example",
    "base": {"id": "d001", "sha256": "<回执中的草稿摘要>"},
    "instruction": "根据用户交接的内容设计画面、动作、文字和声音。"
  }
}
```

本次结果返回 document 后读取并审查，再以相同引用调用 review_design。needs_input/failed 留下的草稿可查阅，但未完成设计不能标为 adopted。新稿未交接不改变旧制作依据；重新交接后，原设计须更新后才能用于新制作。

## 图片配音与本机音乐

普通视频制作中，设计采用后由项目 AI 在任务内完成素材与配音决策，外部 AI 传达要求、审查结果。下面的独立生成入口继续用于用户明确要求的素材任务和诊断，不要求外部 AI 逐项准备后再交制作。

`search_assets` 按 query、role、offset/limit 检索配置目录及所选 purpose 区域的既有作品素材。候选携带 source 引用、用途和使用状态；名称检索不证明内容合适。项目内工具按明确 source 检查并复用，复制原字节并保存来源，旧版本不变。

项目制作 AI 在现有 Agent 中获得以下动态工具，属于当前制作的内部操作，不创建另一轮外部制作任务：

| 工具 | 作用 |
| --- | --- |
| intentframe_media_capabilities | 查看本轮生成配置、素材库和实际检查边界 |
| intentframe_search_assets / intentframe_inspect_asset | 检索候选、查看真实图片、核对音频信息；prepareAudioPreview=true 保存试听片段供用户播放，不向模型传音频 |
| intentframe_reuse_asset | 校验所选来源并复制进作品和当前工程 |
| intentframe_generate_image / intentframe_synthesize_speech | 内部生成图片或精确脚本台词，记录父任务身份和独立请求；图片可指定 background 为 transparent |
| intentframe_download_image | 保存原生网上搜索找到的公开图片及来源页面、使用说明 |
| intentframe_set_audio_playback | 保存全量声音播放安排及命名事件，生成工程可直接引用的播放组件和时间数据 |
| intentframe_preview_video | 渲染当前源码快照的全片或 frameRange 指定范围并返回实际图片；预览不是最终成片 |

设计阶段仅开放前三项只读能力（能力查询、检索、检查）及原生搜索。内部写工具使用稳定 operationKey，相同编号不能换输入；结果未知不能换编号重发。项目保持父制作状态，工具写操作当前串行。生成、导入和预览都保存本机证据，任务结束后仍可读取。

声音编排的每个 clip 指定 id、assetId、startMs，可选 trimStartMs/trimEndMs、playbackRate、volume、fadeInMs/fadeOutMs 和 cues。cue 给出 name、quote、edge（start/end），重复文本还须指定 occurrence。只取供应商提供的字词边界，不能在词内插值或按字数均分。工程导入工具返回的 `ProjectAudio`、`playback`、`cueFrame`；字幕读取同一数据，事件名为“clip.id.cue.name”。修改配音后重新调用工具，保留旧音轨与历史编排记录。生成文件不可手改，时序索引是派生依据而非对成片重新转写。

本机文件通过 import_asset 提交绝对路径，指定 role 为 reference/image/narration/music 及 description，可关联 document。项目复制并验证，不移动或覆盖原文件。get_asset 按素材编号取得固定本机位置和媒体元信息。

GPT 图片通过 generate_image 调用项目 API 适配，必须传 workId、document、prompt、description；referenceAssetIds 可选已有图像，用于参考编辑。只有配置就绪后实际调用，当前每次生成一张图。生成图需作为设计依据时，用 design_video 形成引用该素材的新脚本，再审查采用；不会偷偷替换已采用脚本的附件。

人声文本在脚本中这样标识（以下为格式示意）：

```speech:line1
实际要朗读的原文。
```

声音语气、表演动作和制作指令写在围栏外，关联适用的片段编号。read_speech_text(workId, design) 返回准确片段；synthesize_speech 必须给出已采用脚本 document、明确的 segmentIds、description，可选 speechRate 和 voiceInstruction。项目只提交所选原文，保存音轨、声音指令和字词时间。用户自录音通过 import_asset 的 narration 导入。

`voiceInstruction` 是独立的自然语言声音要求，项目限制为 1–2000 字符；调用方 AI 依据已采用脚本填写，例如“轻声、温柔，开头带一点犹豫，最后真诚坚定”。`description` 只说明素材用途，不能代替此字段。指令作用于本次合成的全部片段；要求不同的片段须分开调用。项目将指令放入豆包 `req_params.additions` 的 `context_texts`，按接口要求将 additions 序列化为 JSON 字符串，台词不混入指令或标签。未提供指令时保持普通配音；空白指令或不支持的模型在发送前拒绝，不登记生成请求，也不静默换模型。

当前支持声音复刻 2.0 的表现力增强模型，以及语音合成 2.0 公版音色；复刻音色须同时配置 `resourceId: "seed-icl-2.0"` 与 `model: "seed-tts-2.0-expressive"`。模型名不能填到 resourceId。这里只接入自然语言声音指令，未接入局部语音标签；指令被发送、服务返回音频和声音听感符合要求是不同的验证结果。

背景音乐使用用户提供或指定的本机文件，以 music 导入。本轮明确的素材用 assetIds 传给 produce_version，脚本附件也会加入制作输入。代码只引用工程内的 public/assets 副本，不引用外部原路径。实际声音仍须由具备听音能力的外部 AI 或用户检查。

服务未配置时 get_runtime_info.mediaServices 返回 false，生成工具明确拒绝；不为了让流程继续而伪造图片/音轨。接入条件和权限见[本机生成服务配置](../config/README.md#图片与豆包语音)。

## 项目准备与外部审查

新流程先看制作结果的 delivery。status=ready_for_external_review 时，versionId 和 videoLocation 指向已通过项目内检的本次交付；内部修复可能让最终版本号不同于首次生成版本。not_ready 时说明未解决问题，不能把历史诊断版本当作合格结果交用户。

get_review_materials(workId, versionId) 返回实际视频位置、采用脚本、批次 indexRef/indexLocation、帧图和拼图的 location、原视频时间、混音位置、项目检查记录及 readyForExternalReview。外部 AI 应实际读取交付版本的材料独立审查，不以项目通过代替自己的判断，也不在外部临时目录自行抽帧。

支持图像工具结果的客户端可直接调用 read_media_image：素材使用 source={kind:"asset",assetId}；审查帧或拼图使用 source={kind:"review",versionId,indexRef,imagePath}，imagePath 取索引里的 path。工具返回 MCP 图像内容和来源说明，文件仍由项目保存；单图消息上限 8 MiB。CLI 文本客户端只打印来源元信息，实际查看须由能接收图像的外部 AI 客户端完成。声音仍通过实际音轨文件交给具有听音能力的客户端。

prepare_review_materials 是后台工具。外部 AI 发现材料不足时，先按版本保存问题，再调用该工具；不传 ranges 时，由项目 AI 结合脚本、材料和已有反馈判断补充范围。明确需要定位时也可传 ranges：startSeconds、endSeconds、fps、reason；项目保存新批次并检查。新流程若发现明确实现问题，会自动修复并复查，因此须使用返回的 versionId 和 delivery 接续审查；requestedVersionId 保留起始版本。轮数上限与覆盖限制见[项目回看规则](../docs/workflow.md#主-ai-回看与修正)。

新流程 record_review 须包含 materialIndexes，值使用实际读取批次的 indexRef（数据根目录内相对路径）；notes 说明查看过哪些材料、问题位置、连续播放与听音是否完成。status=passed 只在声明的检查范围内成立；用户认可另存。文件缺失或变化时不能继续登记为原材料的审查。

available 只表示材料覆盖充分，还须检查 quality 与 readyForExternalReview；needs_attention 表示材料仍有疑问。项目内检的 quality.status 区分 passed、needs_repair、needs_confirmation、not_checked；已知问题会内部修复或返回具体阻塞。后台 waiting_input 可能表示待确认或修复达到上限，不能当作完成。failed/unknown 沿原执行核对恢复。旧任务未启用设计流程时，legacy_unchecked 不代表内检通过。

## 固定请求模板

本节是当前接口的常用制作请求模板，供外部 AI 准备工具参数；不是要求用户填写表单。结构和字段以[实际工具定义](../src/mcp/server.ts)为准，其他操作按其对应章节及工具定义使用。

**填写规则：**

- 下方写操作 JSON 都是传给 `prepare_operation` 的输入。准备成功后，保存返回的完整 `arguments`，再调用 `name` 指定的目标工具；同次操作重试使用已保存参数，不重新套模板生成编号。
- `work-example`、`feedback-example` 和示例版本是占位示例。必须替换为实际回执或查询取得的编号；不能把示例编号发送到真实任务。新操作编号由准备工具生成，已有任务和版本编号仍由调用方选对。
- 字段中的说明性文字必须替换为本轮真实内容；用户原话完整保留，AI 的整理或推断单独注明。示例中的用途、阶段、方向变化和审查结论均不是固定答案。
- 必填项缺失时先取得必要信息。可选项不适用时省略，不用空字符串、虚构编号或 `null` 占位。主台词、备选及未定事项按真实需求保留，不擅自定稿。
- 不提交客户端发送时间；模型选择、执行状态或检查摘要等工具未支持的请求字段也不添加。局部反馈的可选位置按[定位说明](#制作定位与确认)补充。

### 创建作品

创建任务保存原始需求及首版 Markdown 草稿，不开始设计或制作。根据用户明确用途选择 `test` 或 `production`；下例的 `test` 仅为示例。需求正文按同一文字结构说明原话、执行要求、保留内容和未定事项，真实没有的事项写明“无”，不编造内容。

```json
{
  "name": "create_work",
  "arguments": {
    "title": "本轮作品标题",
    "brief": "用户原话：完整保留本轮原话。\n本轮执行要求：说明范围与约束，区分 AI 整理的内容。\n保留内容：已有明确要求或无。\n未定事项：尚待决定的内容或无。",
    "purpose": "test"
  }
}
```

执行 `create_work` 成功后，从结果取得真实作品编号，后续沿该编号操作，不再通过参数切换用途。

### 首次制作样例

仅用于尚无已有版本的首次制作。`sample` 表示代表性样例；`fresh` 表示启动新的原生会话。准备并执行后，保存返回的执行编号，按下方查询模板取进度。

```json
{
  "name": "produce_version",
  "arguments": {
    "workId": "work-example",
    "kind": "sample",
    "designRef": {"id": "s001", "sha256": "<实际采用脚本摘要>"},
    "assetIds": [],
    "feedbackIds": [],
    "threadMode": "fresh"
  }
}
```

### 提交反馈

先核对用户正在看的版本。下例包含 AI 的执行解释，所以标为 `external_ai`；只有确实属于用户原话的记录才标为 `user`。`changesDirection` 按真实影响选择，不能所有反馈都照抄为 `false`。

```json
{
  "name": "submit_feedback",
  "arguments": {
    "workId": "work-example",
    "versionId": "v001",
    "text": "用户原话：完整保留用户反馈。\n执行解释：说明本轮如何理解该反馈，不增加未获授权的要求。",
    "source": "external_ai",
    "changesDirection": false
  }
}
```

成功后，从回执及必要的分页查询取得本条反馈编号。已知排队或制作期间可以追加针对已登记版本的反馈，回执中的 `receivedDuringExecutionId` 关联原执行；它不会进入已冻结的当前输入。未知执行、恢复占用或目标版本不存在时仍会拒绝，未得到成功回执不能声称已保存。首次任务尚未登记任何版本时，须先查询实际版本，不能虚构目标编号。

用户明确替代或取消旧意见时，在同一反馈请求中增加 `supersedes:["实际旧反馈编号"]`，正文保留本次原话和解释。旧意见仍可追溯，新制作不会自动再选入被替代项；恢复旧要求应另行记录新反馈。

### 按明确反馈修改样例

按[制作前核对基线与反馈](#制作前核对基线与反馈)分别查明反馈指向的版本、实际工程基线和适用范围。下例只处理指定的一条反馈；其他仍有效事项保留。基线理由应说明真实选择，尤其回到历史工程时须交代后续修改如何处理。

```json
{
  "name": "produce_version",
  "arguments": {
    "workId": "work-example",
    "kind": "sample",
    "designRef": {"id": "s001", "sha256": "<实际采用脚本摘要>"},
    "assetIds": [],
    "feedbackIds": ["feedback-example"],
    "threadMode": "fresh",
    "baseVersionId": "v001",
    "baseReason": "说明为什么沿用这个工程，以及已有有效修改如何保留。"
  }
}
```

接续原生会话时才将 `threadMode` 改为 `resume`，并先核对该基线有可接续线程。多个方向之间不能假定省略基线或反馈编号会自动选中用户想要的范围；当前限制见[方向与反馈的适用范围](../docs/data.md#方向与反馈的适用范围)。

### 创建备选方向

先把“新增备选”的真实要求保存为反馈；如果原方向仍有效，不将它标为撤销原方向。下例从 A 的工程创建另一方向样例，保留 A 的源码与确认，明确指定创建备选的反馈。新流程先审查采用新方向脚本；历史任务仍须用户确认对应样例后才能完整制作。

```json
{
  "name": "produce_version",
  "arguments": {
    "workId": "work-example",
    "kind": "sample",
    "designRef": {"id": "s001", "sha256": "<实际采用脚本摘要>"},
    "assetIds": [],
    "baseVersionId": "v001",
    "baseReason": "以已核对的 A 工程探索另一方向，原方向与历史结果保留。",
    "feedbackIds": ["feedback-example"],
    "newDirection": true,
    "threadMode": "fresh"
  }
}
```

### 记录用户方向确认

仅在已经取得用户对明确样例的真实确认后使用。`userConfirmation` 填确认原话，`scope` 写清确认范围；不能由 AI 编造确认。

```json
{
  "name": "confirm_version",
  "arguments": {
    "workId": "work-example",
    "versionId": "v001",
    "kind": "direction",
    "userConfirmation": "填写用户对该样例的真实确认原话。",
    "scope": "说明用户同意继续的方向及其适用范围。"
  }
}
```

### 完整制作

新流程须有用户草稿交接和已采用设计，明确传入 designRef；不把 AI 采用记为用户成片认可。旧任务必须已有用户对明确样例方向的确认，且基线延续该方向。未处理反馈明确传 []；关键方向变化先更新适用设计或旧任务样例。

```json
{
  "name": "produce_version",
  "arguments": {
    "workId": "work-example",
    "kind": "complete",
    "designRef": {"id": "s001", "sha256": "<实际采用脚本摘要>"},
    "assetIds": [],
    "feedbackIds": [],
    "threadMode": "fresh",
    "baseVersionId": "v001",
    "baseReason": "说明该基线如何延续用户已确认的方向。"
  }
}
```

### 保存实际审查结果

只记录已经实际检查的版本和范围。下例的 `needs_changes` 表示发现问题；仅在对应范围确实通过时改为 `passed`。静态或技术检查不能充当完整观看审查。

```json
{
  "name": "record_review",
  "arguments": {
    "materialIndexes": ["<实际检查批次的 indexRef>"],
    "workId": "work-example",
    "versionId": "v001",
    "status": "needs_changes",
    "notes": "实际检查范围：具体说明。\n发现与结论：写明依据。\n未检查部分：明确保留。",
    "source": "external_ai"
  }
}
```

用户认可完整成片时仍调用 `confirm_version`，将 `kind` 改为 `acceptance`，填写实际完整版本和用户原话；方向确认与审查通过不能替代成片认可。

### 查询受理结果与当前作品

以下是直接传给只读目标工具的参数，不调用 `prepare_operation`，不生成新操作编号。执行编号和原操作编号必须取自已保存的实际请求或回执。

| 目标工具 | 固定参数形状 | 填写依据 |
| --- | --- | --- |
| `get_operation` | `{"operationId":"原操作编号"}` | 已保存请求的编号，用于核对是否已受理或已完成 |
| `get_execution` | `{"executionId":"原执行编号"}` | 后台受理回执中的编号，用于查询同一次执行 |
| `get_work` | `{"workId":"work-example","offset":0,"limit":20}` | 实际作品编号；还有下一页时沿返回偏移继续查询 |

取得后台受理回执后沿原执行编号查询。查询结果和实际完成含义按[后台执行说明](#后台执行查询与停止)核对，不能以重新提交制作代替查询。

## 后台执行、查询与停止

后台工具包括 revise_draft、design_video、import_asset、generate_image、synthesize_speech、prepare_review_materials，以及原有制作、渲染、整理和恢复。新稿件结果查看 result.document；素材结果查看本机 location；材料结果查看 batches。不要对所有结果都假定存在视频版本。

`produce_version`、`render_version`、`organize_experience`、`recover_work` 返回 `status:"accepted"` 和 `executionId`。执行编号沿用本次操作编号；受理、实际执行和作品状态分别记录。其他工具仍在本次调用内返回结果。重放旧的同步操作时沿用其原回执，不补造后台编号。

使用 `get_execution` 查询 `executionId`，按返回的 `pollAfterMs` 安排后续查询，不以不断重发制作代替等待。查询反映实际阶段与结果；进程存在不证明工作正在推进，也不构成完成依据。

| 执行状态 | 含义与下一步 |
| --- | --- |
| `queued` | 已受理，工作进程尚未领取，继续查询。 |
| `running` | 正在执行，查看当前阶段；有停止请求时仍要等待真实结果。 |
| `succeeded` | 本次动作已取得明确结果，读取 `result`；整理或恢复完成不等于视频已完成，更不等于用户认可。交付前按明确版本核对作品和文件可用性。 |
| `waiting_input` | 制作或恢复需要补充信息，向用户说明缺口，保存答复后按原作品接续。 |
| `failed` | 本次动作明确失败，先查看错误及保留结果，再决定必要的后续操作。 |
| `cancelled` | 本次动作已确认未开始或已经停止，不表示撤回此前产生的结果；已有文件仍保留。 |
| `not_started` | 工作进程未领取便退出，核对启动环境并通过恢复入口处理原占用。 |
| `unknown` | 原执行、身份或写入结果尚未核清，保留原占用，按[原调用恢复](#原调用恢复)核对。 |

若结果已返回但 `workerAlive` 仍为真，进程可能正在收尾，按建议间隔再查询。用户之后回来询问时仍用原编号查询；当前不保证聊天结束后客户端会自动持续查询或主动通知。Mac 关闭、休眠或系统限制后台进程时，不能承诺任务继续推进。

用户明确要求停止时，为 `cancel_execution` 准备新的操作编号，并以 `executionId` 指定要停止的原执行，可附 `reason`。`stopRequested:true` 只表示停止请求已保存。原生执行无法确认终态时仍返回未知，不能擅自删除占用或新建制作。短暂的交接锁、恢复保护或记录损坏无法核清时，保留现场交由维护核对。

## 制作、定位与确认

准备 `produce_version` 请求时提供 `workId` 和 `kind`（`sample` 或 `complete`），基线与反馈参数按[制作前核对基线与反馈](#制作前核对基线与反馈)选择。`threadMode` 默认为新会话，也可使用 `resume` 接续原生线程；两者都要读取当前任务事实，`resume` 还须有该基线的原生线程。调用会使用现有模型额度。

`purpose` 是任务用途，`kind` 是制作阶段。正式任务也可以先做 `sample`；测试任务同样须满足适用的草稿交接和设计采用条件，旧任务仍须方向确认。

新流程完整制作依据明确的已采用设计，旧任务仍要求用户真实的样例方向确认。`confirm_version` 只转录用户对明确版本的确认原话，不能把设计采用、样例确认、AI 自检或测试目的当作成片认可。审查用 `record_review` 单独记录观看范围、问题与来源；文件存在不证明审查通过。

整片反馈用 `submit_feedback` 保存 `workId`、`versionId`、`text` 和 `source`，无需位置。局部反馈可附：

```json
{
  "location": {
    "description": "开场标题下方的说明字幕",
    "precision": "approximate",
    "startSeconds": 1.2,
    "endSeconds": 2.8,
    "quote": "原字幕内容",
    "requestedChange": "与主体拉开距离"
  }
}
```

这是定位字段示例，须与真实原话和目标版本一起提交。`verified` 表示已核对，`approximate` 表示近似线索，`unresolved` 表示待定位；程序只检查时间有序和已知时长范围，不能代替画面核对。旧版本位置在新基线上需重新定位。

## 原调用恢复

recover_work 也核对草稿/设计和素材的原执行。稿件沿原只读线程与输入补存正文，不重发模型；素材只有本机保存了可校验原字节时才能补登记，没有输出且服务结果仍不明时保持 unknown，明确拒绝保留 failed。恢复后查询原 executionId 可取得实际完成、待输入或失败结果；原受理回执、失联记录及已存在的首次返回计时继续保留。核对原恢复结果后再继续，不能改编号重做可能已收费的请求。

新建 `recover_work` 请求，提供原 `workId`，受理后通过 `get_execution` 查询恢复结果；默认可以继续已核实完成工程的渲染、项目内检及尚未开始的必要修复，`render:false` 只核对及补存。原工作进程仍运行或身份无法核对时拒绝另行恢复；原进程退出也须核对原生调用及工程证据。不会重发未知原调用；已核回内检结论且仍需修复时，会沿原操作继续创建修正版，不重置修复轮数。单纯补存不创建新版本。

| 恢复结果中的情况 | 后续动作 |
| --- | --- |
| `recovered` | 读取任务中的制作状态、媒体可用性及经验保存情况；补存成功不等于作品已经通过审查。 |
| `running` | 原进程或原执行未结束，继续查询，不重发制作。 |
| `not_sent` | 原任务尚未发送，现场保留；核对准备失败原因后，可用新操作接续。 |
| `needs_verification` 或 `unknown` | 缺少当时工程证据、原身份或可靠结果；保留原文件与保护，先补充核对依据。 |
| 明确错误 | 根据错误核对原记录和文件；恢复保护本身异常留下占用时由维护方人工核对，不能仅按时间删除锁。 |

`render_version` 用于已有完成工程的产物恢复，不调用模型；须先解决未知执行或未完成草稿。它也会识别预览缺口，仅缺预览时从原视频抽帧；补图失败可沿原编号核对，`recover_work` 的 `render:false` 只检查、不补图。补存成功且视频就绪后，后台制作的执行记录补充恢复结果，原停止或未知记录仍保留，原受理回执保持不变；旧同步操作仍按原规则补齐回执。其他本地写操作若在回执保存前中断，须按原编号和现场核对，不自动重放。

## 经验整理与查阅

草稿修改、设计修订和设计审查也会进入待整理来源。organize_experience 可在尚无视频时整理稿件候选，保存经验的来源可使用 kind:document、purpose、workId、documentRef。仅有稿件来源不能宣称画面效果已验证；评价保留新旧正文、修改指令与采用依据。

1. `learning_status` 返回本任务待整理的原始来源、剩余数量、已保存批次及保存错误。来源较多时先处理当前批次，再重新查询；原文未检查的部分保持待处理。
2. `organize_experience` 受理后由现有项目主 AI 只读分析当前批次，用 `get_execution` 取得结果，会使用模型额度；存在待保存结果时先接续保存，不再调用模型。没有可推广发现时允许没有候选。
3. `search_experience` 用 `query` 分页查简要索引，`read_experience` 用返回的确切 `id`、`revision`、`sha256` 读取正文并核对来源。搜索未命中与读取失败不同；不能从索引摘要直接认定经验适用。
4. 外部 AI 通过 `save_experience` 保存人工审阅后的候选或经验更新，更新须带 `id` 和当前 `expectedRevision`。正文要求问题、方法、条件、限制、来源和状态。主 AI 自动整理只形成候选，不自动升级为已验证经验或用户偏好。

`verified` 需说明实际复查范围并关联可用且复查通过的版本，`withdrawn` 停止后续采用并保留历史；`evaluation_only` 不进入普通制作查找。来源指定查找区域、作品、版本、工程摘要和原反馈编号，原反馈须属于该版本。部分来源缺失时保留明确错误，不把现有文件补认为历史依据。

制作中的主 AI 可调用经验查找、经验正文读取、反馈列表和反馈原文四个动态工具。实际读取的内容留存于本次执行，最终声明的采用经验必须属于实际读取版本；这些机制不保证语义判断正确。跨作品原始事实仍从来源任务和本机文件查阅，未建立通用记忆或语义检索平台。

## 前后比较

在同一个连接中调用 `create_comparison`，提供 `comparison`；工具按比较任务的定义自动使用测试区域，无需另传用途或切换服务：

- `title`、`brief`、`change`：本轮问题、共同原始需求和要检查的改动。
- `kind`：`creation`、`revision` 或 `retrieval`；修改比较须同时指定共同 `base` 与 `revisionRequest`。
- `knowledgeRefs`：双方可读取的确切经验版本列表，允许空列表；创建后不跟随共享经验更新。

新建比较时，标题限额为两侧任务的名称标记预留长度；原始需求、共同修改要求及分隔文字按拼接后的总长度校验，具体限额以工具参数为准。超限或空白需求在写入前拒绝，不截断原文，也不创建比较或作品记录；已保存的历史比较仍按原格式读取。

创建返回修改前后两条作品编号，不启动模型。调用方在对应系统版本下各提交一次 `produce_version`，固定共同需求和基线，并查询两侧后台结果后再评价；临时添加反馈或再次制作不能继续算作该轮首稿比较。比较不会自动切换 Git 版本。切换系统版本后须重新启动服务，不能仅修改磁盘文件便认定正在运行的进程已经更新；实际条件与未受控差异应在评价中说明。

外部 AI 或用户实际检查两份结果后，用 `record_comparison` 提交版本、`verdict`（改善、退步、混合或无法确定对应 `improved`、`regressed`、`mixed`、`inconclusive`）、`observations` 和 `source`。说明观察范围、耗时与人工投入、未受控差异；不把模拟产物或技术检查写成作品效果。

比较未结束时，该轮候选只暂存在作品记录。评价保存后，对每条相关任务调用 `publish_test_experience` 发布已暂存的候选，再查看 `learning_status` 整理新评价。重复发布不会重复累积；暂存正文变化或来源无法核实时停止并保留待办。

## 维护与验证入口

从仓库根目录按[系统回归说明](../docs/maintenance.md#系统回归的范围)运行 `npm run check` 和 `npm test`。测试用隔离目录与合成数据，媒体和备份测试使用真实本机工具；它们不能证明模型语义能力或视频效果。真实模型接入试跑为 `npm run test:local`，会使用现有模型额度；备份为 `npm run backup:local`，始终备份配置的整个资产总目录。
