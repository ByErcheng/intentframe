# 数据与经验

[系统架构与技术选型](./architecture.md) · [制作与运行流程](./workflow.md)

长期保存作品需求、素材、工程、进度、版本、反馈与认可记录，以及跨作品经验和验证证据。保留边界遵循[数据管理约定](../AGENTS.md#数据管理)。

## 记录组织

采用文件与必要索引，格式和管理工具见[技术选型](./architecture.md#已选技术)。同一事实只维护一处权威记录，其他内容通过稳定标识与引用关联；先读任务入口，再按任务、版本和记录类型查阅所需内容。

本页给出保存与接续的设计要求；当前支持范围与缺口见[实现状态](./architecture.md#当前实现与下一步)。

- **Markdown** 用于便于阅读的需求、制作决定及解释性内容。
- **JSON** 用于需要程序读取的状态与关联。
- **JSONL** 仅按需保存项目执行事件，原生技术日志和长期证据的分工见[日志与过程记录](./workflow.md#日志与过程记录)。

作品记录关联以下内容：

| 内容 | 保存与关联要求 |
| --- | --- |
| 需求 | 原始输入、参考、约束和后续变更，区分原始需求与当前有效需求 |
| 任务与执行 | 制作决定、当前进度、已有作业和产物、失败或未确定状态，支持核对后接续 |
| 作品版本 | 实际作品、对应工程与素材、制作条件及结果 |
| 审查与反馈 | 按[反馈处理](./workflow.md#反馈处理)关联原始反馈、目标版本、实际修改、新版本和复查结果，保留未解决事项与明确的用户确认 |
| 经验依据 | 为跨作品经验提供来源案例与证据引用 |

### 当前最小记录

每条作品以独立的任务记录为查阅入口，保留原始需求，并使用稳定编号关联各项资料，避免标题变化或重名影响接续。

- 工程按版本保存，媒体与对应作品及版本关联。
- 版本记录制作范围、进度、来源版本、本次及此前已处理的反馈、执行关联、结果说明和检查依据。
- 保存可核对的工程组成、素材与依赖条件，支持检查文件是否变化和后续接续；旧记录按已有证据使用，不补造缺失内容。
- 制作状态、审查结果和用户认可分别保存；方向确认关联明确样例与范围，不自动认可后续成片。
- 必要执行记录随作品保存。结果未知或前次操作未正常结束时，须先核对进度，不能盲目重发。
- 记录更新须避免并发覆盖或留下不完整内容；异常退出后的状态仍需核对，目前不自动恢复。

### 当前状态与历史记录

当前状态用于决定下一步，历史记录用于保留实际发生过的审查与确认。更新当前状态时，历史事实仍须可追溯：

- 每次审查分别保留结论、说明、来源和检查时间，并明确哪一次是当前最新结果。不同来源的审查独立记录，最近一次通过不代表其他来源也已通过。
- 用户每次确认分别保留原话、对应版本、确认类型、范围及已知时间；当前有效的方向确认与具体版本的认可状态分别表达。方向变更可以使此前方向确认失效，重复确认可以更新当前状态，但此前发生过的确认仍保留。
- 更新旧记录时保留其中已知的审查与确认；不编造缺失的确认时间，也不能恢复此前已被覆盖且没有其他证据的内容。只读查询不改变历史。

### 需求与修改关系

原始需求、反馈和用户确认保留原文，包括原有缩进和换行。交接与保存对同一输入的有效性要求应保持一致；必要检查不能改写原话，无法接受的输入须明确说明原因。

当前有效需求由原始需求和仍有效的变更共同组成，保留来源及替代依据；记录已处理、未处理的事项及对应结果，不能因本次只处理一条反馈而丢弃其他仍有效的要求。

反馈目标版本用于定位意见，修改基线版本用于确定本次延续的工程。基线应与当前有效需求及已完成修改一致；回到历史版本制作须记录依据和对后续修改的处理，不能把反馈所指的旧版本自动当作当前基线。结果关联本次实际处理的反馈、基线和新版本。

### 草稿与完成工程

草稿能否接续编辑，与工程是否已完成并可直接渲染，须分别判断。制作因等待补充信息或明确失败而停止时，保留已有工程、已处理反馈和未解决事项；核对来源、版本与实际进度后，可以延续其中仍有效的修改。未完成的草稿不能当作完成工程直接渲染，也不能把无法核实的修改记为已完成。

接续制作应从最新有可核对记录的工程开始，带上最近一次结果说明和待补充信息，延续仍有效的修改，并保留原草稿。文件与记录不一致时先核对差异，不自动退回更早工程。完整制作另须满足[方向确认与基线要求](./workflow.md#试做与方向确认)。

直接重渲染须先确认工程已完成，并能依据[已有完整性证据](#版本对应与完整性)核对工程与对应版本。执行结果未知时，先按[中断与失败处理](./workflow.md#中断与失败处理)查清原执行；文件存在不能证明制作已经完成，也不足以确定可以安全接续。

### 版本对应与完整性

一个可交付版本须能关联到完整制作源码、实际使用的素材、依赖与制作条件，以及对应成片和检查证据。用可核对的清单或等效方式识别工程及其引用文件，不能只凭入口文件判断整个版本未变；共享依赖可以引用，但须能确定使用的内容。

内容修改生成新版本，历史版本保持可追溯。已有工程或产物在记录外发生变化时，应报告差异；恢复原版本须核对与原记录的对应关系，文件存在或媒体规格相同不足以证明对应正确。输出规格从实际媒体取得，再与工程要求比较。

版本的历史完成、审查与认可记录和文件当前是否可用分别表达。文件缺失、损坏或来源不明时明确标记，不将其作为可用成片交付；修复可用性也不能改写真实发生过的用户确认。

制作所用的源码与素材须纳入对应版本的保存范围，使用的依赖也须有可核对依据。查询时说明工程与成片当前是否可用，同时保留历史确认。旧记录若只能证明单个源码文件的内容，就只按这一证据范围使用；涉及其他文件时须先核对并创建新版本，不能补认此前未保存的完整工程证据。

成片已经生成而任务记录尚未补全时，接续须先核对工程、成片与版本的对应关系，再补齐记录。恢复丢失的已记录成片时，文件内容须与原版本完全一致；不一致的恢复结果保留并说明差异，已有来源不明或损坏的文件不自动覆盖。

迁移数据根目录时更新本节及导航链接；作品内部优先使用稳定编号与相对引用，避免把本机绝对路径复制到每条创作记录。

### 系统测试记录

系统测试代码与不含真实任务数据的可复用夹具位于 [tests/](../tests/)，可运行的验证入口位于 [scripts/](../scripts/)。测试过程产生的临时记录使用系统临时目录或 [.cache/](../.cache/)；经筛选需要长期保留的系统验证证据放在本机 [validation/system/](../../intentframe-data/validation/system/)。具体作品的验证证据随该作品保存在 `works/<作品编号>/verification/`。

证据须保留必要的来源、适用条件及原始结果，避免混入凭据或无关聊天。测试代码可以进入系统仓库，实际执行产生的任务、会话、作品、反馈、日志和报告不随代码提交；作品的保留案例和参考评价仍使用上表中的验证材料入口。

已有证据从[本机数据入口](../../intentframe-data/README.md)查找。临时结果经筛选后再转入本机长期目录；当前能力范围见[本机制作验证](./architecture.md#本机制作验证)。

## 存储与备份边界

- 数据目录在系统工作区之外，默认沙箱不自动覆盖。正式制作前须落实所需目录权限，文档链接不授予访问权限。
- 保留验证材料不纳入普通制作的检索范围，读取控制随验证流程设计；目录分开本身不构成自动隔离。
- 作品及其他长期资产使用本机文件、版本目录和本机备份维护；不建立作品 Git 仓库，也不将实际任务记录或运行证据提交到系统仓库。
- 按用户选择，Restic 备份保存到同一台 Mac 的另一个文件夹 `/Users/yan/ercheng/intentframe-backups/`，由 [backup-local.ts](../scripts/backup-local.ts)按需执行；不设置定时任务或自动删除快照，恢复写入新目录，不覆盖原文件。
- 备份包含系统源码、文档、锁文件和创作数据，排除依赖安装目录、缓存、Git 内部目录及密钥文件。Restic 密码位于备份根目录的 `access/password`，权限仅当前用户读写，不进入项目或日志；这属于同机文件夹备份。
- 缓存清理不应影响项目运行、未完成任务的接续或已保留结论的追溯。可重建内容按需清理，仍有使用价值的记录保留，长期任务事实与必要原始证据按[日志保留要求](./workflow.md#日志与过程记录)转入正式记录位置；临时缓存、未经筛选的聊天和运行日志不整体归档。

已完成一次本机备份恢复验证；执行时间、快照、恢复位置及逐文件核对结果仅保存在本机[备份验证记录](../../intentframe-data/validation/system/local-backup/)。历史报告描述当时路径和检查范围，不随文件迁移改写原始事实。

备份与恢复须保留可核对的一致任务状态及其关联文件。备份前的数据、恢复结果和备份结束时的数据应在文件清单、内容及读写和执行权限上保持一致，包括文件、目录及备份源根目录，避免恢复后的脚本内容相同却无法执行。发现新增、删除、内容或权限变化，或存在尚未解除的作品操作占用时，不能报告一致性验证通过。核对失败时保留已有备份；目前仍需避免其他程序在备份期间修改数据。

## 首版接续修改范围

在同一制作环境中，换一个 AI 会话仍能接续修改：

- 从视频版本找到对应工程、必要素材和制作条件。
- 知道如何预览、修改和再次导出。
- 根据反馈生成新版本，保留旧版本及修改关联。

验证时，新会话依据保存记录选定修改基线，完成明确反馈对应的修改并导出新版本，同时核对仍有效的需求和此前修改得以延续、旧版本保持完整、修改关联可查。只找到工程或重新渲染旧工程，不能单独证明接续修改能力。

跨机器、跨工具迁移需要另行验证，不作为首版接续修改的完成条件。

## 经验积累与使用

主 AI 或现成分析能力从作品与反馈提炼用户偏好、候选经验和方法，[检查与验证](./workflow.md#证据与验证范围)提供效果证据。候选与已验证经验的区别遵循[改进与验证约定](../AGENTS.md#改进与验证)。

| 分类 | 标准 |
| --- | --- |
| 必须项 | 保留经验的来源、适用条件和验证状态；使用前判断是否适合当前任务；已验证结论关联实际案例和结果，用户当前要求优先。 |
| 可以项 | 从重复问题、有效修改或用户明确偏好中提炼候选经验，先小范围试用，再依据实际结果更新、修正或撤销。 |

一次针对具体作品的反馈不自动变成长期偏好。每次制作只读取相关经验及其条件和依据，不要求每次交付强制生成经验总结；保留验证材料不进入普通制作输入。

作品与反馈 → 提炼候选经验 → 验证效果 → 更新状态与适用条件 → 在后续任务中按条件使用。作品制作可以独立推进，经验提炼与验证按需开展。
